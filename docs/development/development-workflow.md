# HelixWeave 开发流程

每项交付由一名负责人跟到验收。工单保存需求、分工、PR 和结论，仓库保存需要随代码演进的契约。
已有 spec 时，在工单链接对应版本和验收条目。当前优先级见[产品路线图](workflow-platform-agent-roadmap.md)。

## 设计写多深

| 改动 | 开工前写什么 | 例子 |
| --- | --- | --- |
| 行为已有约定，修复范围局部 | 在工单或 PR 写复现、预期和验证方法。文字或链接修正可直接写进 PR | 已约定的筛选条件少返回一条记录 |
| 新用户行为，沿用现有契约 | 在工单写短 spec，说明入口、状态变化、失败时用户看到什么，以及验收用例。实施者据此列短计划 | 在查看器里勾选和移除轨道，刷新后保留选择 |
| 改变公共接口、持久化身份、执行语义、跨系统边界或科学结果解释 | 在仓库写或修订聚焦的 spec；有长期架构取舍时记录 ADR。写清兼容性、旧数据、故障或重试行为以及验证方法 | [实验目录与运行快照绑定](../architecture/experiment-catalog-m0-contract.md)、[产物发布与来源](../architecture/artifact-publication-provenance-decision.md) |

设计深度随实际改动调整。例如轨道选择可以先写工单短 spec；如果需要扩展宿主和查看器的消息协议，先把新增字段、旧调用行为及失败用例补到协议文档，再改两端代码。

## 何时可以开始实现

主持人在分派实现或开始改产品代码前，先对照当前源码核实以下三点。

1. **行为已定。** 说得清谁从哪个入口操作、成功时看到什么，以及本次要处理的失败和边界场景。
2. **方案可执行。** 关键取舍已有结论，写明受影响的模块、接口、数据及依赖。会改变用户行为、科学解释或历史兼容性的待决问题，先交给有决定权的人处理。
3. **结果可验收。** 实施者和复审者能从同一个具体例子得出相同的通过条件，知道通过哪个入口取得证据。

满足后，主持人在原工单或 PR 记录“可实施”、所依据的 spec 版本或工单修订，以及验收用例，再派发实现。
条件未齐时，下一步写成具体的设计问题，负责人可以继续读代码、复现或验证假设。
已有契约直接引用适用条款；局部修复把复现、改法和预期写在同一条记录即可。
授权范围内的技术取舍由主持人裁决；属于项目负责人的产品或权限决定交回本人。

## 从需求到合入

| 环节 | 谁来做 | 交给下一步的内容 |
| --- | --- | --- |
| 明确需求 | 主持人查现有代码、工单和已接受的契约，和提出者确认会影响产品行为的选择 | 谁在什么入口完成什么事、本次范围、至少一个可观察的验收结果 |
| 设计与写 spec | 设计负责人按上表选择载体，写下方案、取舍和依赖；把需要项目负责人决定的事项单列 | 实施者可据以开发、复审者可独立判断对错的 spec；复用旧 spec 时注明哪些条目适用 |
| 拆分与执行 | 主持人按可单独验收的结果分派，每项一位实施者。迁移链或同一公共接口指定一位集成者。实施者可以按需使用技能和子 agent | 有依赖的切片注明先后；每份 PR 对应一个用户结果，附工单、spec、实际改动和定向测试 |
| 复审与返修 | 复审者对照 spec 读实际 diff。涉及数据、科学行为或跨组件契约时，由实施者以外的人或 agent 独立验证关键场景。主持人作技术裁决 | 通过或返修结论、对应提交 SHA、验证过的行为。返修沿原工单提交新 SHA，复验受影响部分 |
| 验收与收尾 | 主持人从正常使用入口核验交付，按已有授权和仓库合入条件处理 | 工单记录已验收的 SHA、PR、测试证据和剩余限制。获准合入后核对主干结果，再交接依赖项 |

实现中若发现需求或契约需要改变，受影响的工作回到设计。更新原 spec 的取舍和验收条件，由主持人复核后继续。
独立小修可在一份 PR 内走完以上环节。合入、部署和权限变更各自沿用项目已有的授权范围。

## 工单短 spec 模板

- **用户行为**：谁从哪个入口操作，操作前后分别看到什么？
- **设计与边界**：由哪个模块负责？复用哪个接口或数据身份？涉及哪些旧数据或调用方？
- **验收**：给出输入、动作和预期结果；附与此次改动有关的空值、失败、重试或历史数据用例。
- **交接**：谁实施、谁复审、依赖哪项交付？完成时补 PR、验证的 SHA、命令和结果。

例如，查看器选文件的验收可以写成：打开 WashU 时选择为空；在查看器内勾选两份文件后，只读取这两条轨道；取消最后一条后回到空选择。用真实接口检查排在第 501 位的目标仍可选，用浏览器检查实际发起的读取。

验证深度按[测试分层](harness.md)选择。科学改动应说明采用的数据、参数和计数单位，以及测试能支持的结论。交接时分别记录本地验证、CI 与尚未验证的行为。
