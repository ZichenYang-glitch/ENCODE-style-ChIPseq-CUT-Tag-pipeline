# HelixWeave v0.3.0 Python identity migration

Checked: 2026-07-25

This record fixes the reviewed package-identity boundary for v0.3.0. It does
not reserve a package name, establish trademark rights, authorize a package
index upload, or rename the GitHub repository.

## Identity boundary

| Surface | v0.3.0 identity |
| :--- | :--- |
| Display brand | HelixWeave |
| Python distribution | `helixweave` |
| Primary CLI | `helixweave` |
| Python import namespace | `encode_pipeline` |
| Compatibility CLIs | `encode-validate`, `encode-manifest`, `encode-dag`, `encode-worker` |
| Workflow IDs | `encode-style-chipseq-cuttag-atac-mnase`, `bulk-rnaseq` |
| GitHub repository | `ZichenYang-glitch/ENCODE-style-ChIPseq-CUT-Tag-pipeline` |

The primary CLI, `python -m encode_pipeline`, and
`scripts/run_local_platform.py` share one package-owned implementation. The
compatibility commands still delegate to their existing implementations.
There is no second run store, worker, adapter, or scientific execution path.

## PyPI occupancy observation

The authoritative PyPI JSON and Simple API endpoints returned HTTP 404 for
`helixweave` on the check date. The easily confused spellings
`helix-weave`, `helix_weave`, and `helix.weave` also returned 404. Under
Python package name normalization:

- `HelixWeave` and `helixweave` normalize to `helixweave`; and
- `helix-weave`, `helix_weave`, and `helix.weave` normalize to
  `helix-weave`.

The legacy `encode-pipeline` JSON and Simple API endpoints also returned 404,
so the migration does not invent a published transition package. These are
time-specific index observations only. They are not trademark searches, legal
clearance, ownership guarantees, or evidence that a later upload will succeed.

## Local candidate transition

The unpublished `encode-pipeline` candidate and `helixweave` must not be
co-installed. Different distribution metadata can otherwise claim the same
`encode_pipeline` files and compatibility scripts; `pip check` does not detect
that ownership collision. The supported sequence is:

1. stop the local API and worker;
2. back up the SQLite database and runtime root;
3. uninstall `encode-pipeline`;
4. confirm its metadata and package files are gone;
5. install the exact `helixweave` wheel or sdist; and
6. verify `pip check`, the import namespace, five console scripts, package
   data, migrations, and both workflow IDs.

The maintained commands and recovery rule are in the
[local trial checklist](../local-trial-checklist.md#migrating-an-old-local-candidate).
Formal build and asset rules are in the
[release checklist](../../RELEASE_CHECKLIST.md).

## Preserved runtime contracts

The migration does not rename `ENCODE_PIPELINE_*` environment variables,
`.encode-pipeline` state directories, Redis queue names, schema identifiers,
workflow-build hash separators, Alembic history, API routes, workflow IDs, the
ENCODE adapter, or the Bulk RNA-seq adapter. Those values remain compatibility
or persisted-runtime contracts rather than distribution branding.
